# Project Tree Generator

## ภาพรวม

Skill นี้สร้าง "ผังต้นไม้" ของโปรเจกต์โค้ด — ไม่ใช่แค่ `ls -R` ดิบๆ แต่เป็นผังที่ตัดไฟล์ขยะออก (node_modules, .git, __pycache__ ฯลฯ) จำกัดความลึกให้อ่านง่าย และแนบคำอธิบายสั้นๆ กำกับแต่ละโฟลเดอร์/ไฟล์สำคัญ โดยดึงความหมายมาจากเอกสารที่มีอยู่จริงในตัว repo เอง (README, docs/, package.json, pyproject.toml ฯลฯ) ไม่ใช่การเดาจากชื่อไฟล์ล้วนๆ

Input ของ skill นี้คือ **โฟลเดอร์ที่มีอยู่แล้วในเครื่อง** — ไม่ได้ทำหน้าที่ดึง repo จาก GitHub มาให้เอง ถ้าผู้ใช้ให้ลิงก์ GitHub มา ให้ clone repo นั้นก่อน (ผ่าน `git clone`) แล้วค่อยเริ่ม workflow ด้านล่างกับโฟลเดอร์ที่ clone มา

## ขั้นตอนการทำงาน

### 1. หาโฟลเดอร์เป้าหมาย

- ถ้าผู้ใช้อัปโหลดไฟล์ ให้เช็ค `/mnt/user-data/uploads` — ถ้าเป็น zip ให้แตกไฟล์ก่อน
- ถ้าผู้ใช้ให้ลิงก์ GitHub repo มา ให้ `git clone --depth 1 <url>` ไปยังโฟลเดอร์ชั่วคราว
- ถ้าผู้ใช้บอกพาธในเครื่องมาตรงๆ ให้ใช้พาธนั้น
- ถ้าไม่แน่ใจว่าหมายถึงโฟลเดอร์ไหน (เช่นมีหลายโฟลเดอร์ที่เป็นไปได้) ให้ถามสั้นๆ ก่อนเริ่ม แทนที่จะเดา

### 2. รัน `scripts/build_tree.py` เพื่อดึงโครงสร้างดิบ

**เสมอ** ใช้สคริปต์นี้ในการเดินไฟล์ — อย่าเขียน loop เดินไฟล์เองหรือใช้ `find`/`ls -R` ตรงๆ เพราะสคริปต์จัดการเรื่องพวกนี้ให้แล้ว:
- ข้ามโฟลเดอร์ขยะมาตรฐาน (`.git`, `node_modules`, `__pycache__`, `venv`, `dist`, `build`, `.next`, `target` ฯลฯ) และอ่าน `.gitignore` ของ repo เพิ่มด้วย
- จำกัดความลึกและจำนวนไฟล์ต่อโฟลเดอร์ ไม่ให้ผังยาวจนอ่านไม่ไหว (สรุปเป็น "... N more" แทน)
- เก็บรายชื่อไฟล์เอกสารที่น่าจะมีประโยชน์ (README, docs/, package.json ฯลฯ) มาให้พร้อมในหัวข้อท้ายผล เพื่อให้รู้ว่าควรไปอ่านไฟล์ไหนต่อ

```bash
python3 scripts/build_tree.py <path> --max-depth 4
```

ปรับ `--max-depth` ตามขนาด repo: repo เล็ก (< ~100 ไฟล์) ใช้ 4-5 ได้, repo ใหญ่ใช้ 2-3 พอ ถ้าอยากดูลึกกว่าที่ default แสดง ค่อยรันซ้ำเจาะจงโฟลเดอร์ย่อยด้วย `--max-depth` สูงขึ้นเฉพาะพาธนั้น

ตัวเลือกอื่นๆ: `--max-entries` (จำนวนไฟล์สูงสุดต่อโฟลเดอร์ก่อนสรุป, default 15), `--format json` (ถ้าต้องประมวลผลต่อด้วยโค้ด), `--exclude "pattern,pattern"` (ยกเว้นเพิ่มเติม)

### 3. อ่านเอกสารเพื่อหาความหมาย ไม่ใช่เดา

จากรายการ "Likely documentation files" ที่สคริปต์ให้มา ให้เปิดอ่านเฉพาะไฟล์ที่จำเป็นจริงๆ — ไม่ต้องอ่านทุกไฟล์:

- **README.md ที่ root** เกือบทุกครั้งควรอ่าน เพื่อรู้ว่าโปรเจกต์นี้คืออะไรโดยรวม
- **package.json / pyproject.toml / Cargo.toml / go.mod** อ่านเฉพาะฟิลด์ `description` เพื่อสรุปสั้นๆ ว่าโปรเจกต์ทำอะไร ไม่ต้องอ่านทั้งไฟล์
- **README.md ย่อยในโฟลเดอร์ลูก** (เช่น `tests/README.md`, `packages/foo/README.md`) อ่านเฉพาะเมื่อโฟลเดอร์นั้นเป็นโฟลเดอร์หลักที่จะโผล่ในผัง และชื่อโฟลเดอร์ไม่ได้บอกอะไรอยู่แล้ว — โฟลเดอร์ที่ชื่อสื่อความชัดอยู่แล้ว (เช่น `tests/`, `docs/`, `.github/workflows/`) ไม่จำเป็นต้องเปิดอ่านไฟล์เพิ่มเพื่อยืนยัน
- ถ้าไม่เจอเอกสารเลยสำหรับบางโฟลเดอร์ ให้เขียนคำอธิบายจากชื่อไฟล์/โครงสร้างที่เห็น (เช่น เดาจาก naming convention ที่คุ้นเคย) แต่บอกให้ชัดว่าเป็นการอนุมาน ไม่ใช่จากเอกสาร — อย่าแต่งข้อมูลขึ้นมาเป็นข้อเท็จจริง

หลักคิดสำคัญ: เป้าหมายคือให้คนอ่านผังแล้วเข้าใจ repo ได้เร็วขึ้น ไม่ใช่พิสูจน์ว่าอ่านทุกไฟล์แล้ว — เลือกอ่านอย่างมีเป้าหมาย

### 4. ประกอบผังพร้อมคำอธิบาย

ใส่คำอธิบาย 1 บรรทัดสั้นๆ (ไม่เกินประมาณ 8-10 คำ) ต่อท้ายเฉพาะ **โฟลเดอร์หลักระดับบนและไฟล์สำคัญระดับ root** — ไม่ต้องอธิบายทุกไฟล์ย่อยในผัง จะทำให้รกและเสียจุดประสงค์ของการสรุป

รูปแบบ:

```
project-name/
├── src/                  # โค้ดหลักของแพ็กเกจ
│   └── ...
├── tests/                # ชุดทดสอบ (pytest)
├── docs/                 # เอกสารประกอบ (Sphinx)
├── .github/workflows/    # CI/CD pipelines
├── pyproject.toml        # metadata + dependencies ของแพ็กเกจ
├── README.md             # จุดเริ่มต้นอ่านทำความเข้าใจโปรเจกต์
└── LICENSE
```

ตัวอย่างสรุปจริงจาก repo `requests`: root มี `src/requests/` เป็นซอร์สหลักของไลบรารี, `tests/` เป็นชุดทดสอบพร้อม certs จำลองสำหรับทดสอบ TLS, `docs/` เป็นเอกสาร Sphinx, และ `pyproject.toml` ระบุว่าเป็นไลบรารี HTTP สำหรับ Python — ดึงมาจาก field description ในไฟล์นั้นเอง ไม่ใช่เดา

### 5. รูปแบบผลลัพธ์

ทุกครั้งที่สร้าง project tree ให้ทำสองอย่างเสมอ ไม่ใช่แค่อย่างใดอย่างหนึ่ง:

1. **แสดงผังในแชท** เป็น code block (```) พร้อมคำอธิบายสั้นๆ ก่อน/หลังถ้าจำเป็น เพื่อให้ผู้ใช้เห็นผลทันทีโดยไม่ต้องเปิดไฟล์
2. **บันทึกเป็นไฟล์ `TREE.md`** ไปที่ `/mnt/user-data/outputs/TREE.md` เสมอ (เนื้อหาเดียวกับที่แสดงในแชท ครอบด้วย code fence ภายในไฟล์) แล้ว present ไฟล์นั้นให้ผู้ใช้ด้วย — นี่คือพฤติกรรม default ไม่ต้องรอให้ผู้ใช้ขอก่อน

ถ้าทำ tree ของหลาย repo/โฟลเดอร์ในการสนทนาเดียวกัน ให้ตั้งชื่อไฟล์แยกกันเพื่อไม่ให้ทับกัน เช่น `TREE-<ชื่อโฟลเดอร์>.md` แทน `TREE.md` เปล่าๆ

ถ้าผู้ใช้บอกชัดว่าไม่ต้องการไฟล์ (เช่น "แค่โชว์ในแชทพอ ไม่ต้องเซฟไฟล์") ให้ทำตามนั้นแทน — นี่เป็นแค่ default ไม่ใช่กฎตายตัว

## ข้อควรระวัง

- **ห้าม** list ไฟล์ทุกไฟล์แบบไม่กรองสำหรับ repo ใหญ่ — จะยาวเกินอ่านไหวและ token สิ้นเปลือง ใช้ `--max-depth`/`--max-entries` ของสคริปต์ควบคุมแทนการพยายาม paste ทุกอย่าง
- **ห้าม** สร้างคำอธิบายที่ฟังดูมั่นใจราวกับมาจากเอกสาร ทั้งที่จริงๆ เดาจากชื่อไฟล์ล้วนๆ — แยกให้ชัดเมื่อเป็นการอนุมาน
- ถ้า repo มีหลาย package/module ย่อยที่ต่างกันมาก (เช่น monorepo) ให้พิจารณาแสดงผังแยกเป็นระดับบนสุดก่อน แล้วถามผู้ใช้ว่าอยากเจาะโฟลเดอร์ไหนลึกขึ้นอีก แทนที่จะพยายามยัดทุกอย่างในผังเดียว
